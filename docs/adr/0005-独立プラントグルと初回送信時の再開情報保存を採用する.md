# 独立プラントグルと初回送信時の再開情報保存を採用する

## Context and Problem Statement

Paseo本体を変更せず、プランON/OFFと承認後の編集モードを同時に選べる必要がある。標準のProvider設定はトグルを提供するが、作成画面での設定・コマンド取得にもセッションを開くため、情報取得を保存会話にしてはならない。

ZCodeのdeferredセッションは未送信では保存されない。native IDだけを最初に渡す方式では未送信の再開に失敗し、初回送信後にハンドルを通知する方式ではPaseoが最初のターン完了まで保存情報を更新しないため、応答中の終了に対応できない。

## Decision Drivers

- Paseo本体を変更しない。
- 情報取得だけではZCodeにもプラグインにも永続レコードを作らない。
- 未送信の再開と、送信済み会話の同一性を両立する。
- 失敗を隠して別の会話に切り替えない。

## Considered Options

- native IDを作成時から渡す。
- native保存後にハンドルを通知する。
- 固定の論理IDを作成時に渡し、初回送信前にnative IDとの対応を保存する。

## Decision Outcome

固定の論理IDと初回送信前の対応保存を採用する。保存形式version 2はlogicalとnativeの識別子を区別し、nativeはZCodeの一覧からのインポートに使う。旧形式の自動変換は行わない。

対応情報はプラグインの配置先から独立したユーザーのstate領域に保存する。一時ファイルの同期と置換を使い、対応可能なOSでは親ディレクトリも同期する。保存失敗なら送信せず、破損・ワークスペース不一致・native会話消失では再開を失敗させる。nativeの保存前に終了した場合に自動で新規会話を作る処理は加えない。

UIは公開Provider設定のplan_modeトグルを使用し、標準Settings2とラベルによるツールチップを採用する。編集モードからplanへ遷移してZCodeの承認後の復帰先を設定する。遷移中の設定通知を抑え、途中失敗時にはランタイムを停止する。

### Consequences

- Good, because 情報取得では永続レコードを作らず、初回応答中にも同じ会話を再開できる。
- Bad, because 再インストール・バックアップ時にプラグインのstate領域も保持する必要がある。
- Bad, because 対応ファイル消失は未送信との区別ができない。state領域の手動削除は再開情報の破棄になる。
- Bad, because 対応保存とnative保存は別処理のため、その間の終了は明確な再開エラーとなる。

### Confirmation

Provider・保存処理の自動テスト、および実Paseo AgentManagerとZCodeを用いた別プロセスでの再開試験で確認する。画面でトグル・編集モード・コマンドを操作し、未送信セッションが一覧に残らないことを確認する。実行結果は検証記録に記載する。

## More Information

Paseoがセッション作成を伴わない設定取得や、初回送信時の保存ハンドルの確実な更新を提供した場合は対応ファイルの必要性を再評価する。実装は検証済みZCode hostの契約に限定する。
