# 最低バージョンと実行時検証でZCodeの更新を許可する

## Context and Problem Statement

ZCode本体・同梱CLIの完全一致とホストファイルのハッシュ照合により、通信仕様を変更しない更新でも起動できなくなっていた。さらに、RPCモジュールのファイル名と短縮export名を固定していたため、バージョン比較だけを緩めてもビルド構成の変更で失敗する。利用者は新しい正式版で起動を試み、問題が発生した場合に診断情報を添えてIssueを報告する方針を選択した。

## Decision Drivers

- 通信に必要な構造を保った更新で、providerの更新待ちを発生させない。
- 未検証のバージョンを許可することと、実際に動作確認したことを区別する。
- 不整合を無視せず、起動時・実行中の失敗を報告可能にする。
- 認証情報、会話、ネイティブの生エラーを診断に含めない。

## Considered Options

- 特定バージョンとハッシュの完全一致を維持する。
- 同じmajorの正式版だけを許可する。
- 最低バージョン以上の全正式版を許可し、必要な構造と実行中の通信を検証する。

## Decision Outcome

Chosen option: "最低バージョン以上の全正式版を許可し、必要な構造と実行中の通信を検証する", because 利用者がmajor更新も含めて起動を試す方針と、その動作保証の限界を承認した。

本体の最低バージョンを3.11.2、同梱CLIを0.16.5とする。semverで比較し、上限は設けない。プレリリース、取得不能・不正なバージョン、最低バージョン未満は拒否する。最低バージョンと動作確認済みのバージョン・ハッシュを分離し、新リリースの監視基準には後者を使用する。ハッシュが異なることだけでは起動を拒否しない。

公式のout/host/index.jsの静的な相対importをes-module-lexerで解析する。同梱Electron内で参照先を読み込み、保持されたMessagePortProtocol・ChannelClientのクラス名と必要メソッド、fromService・toServiceを持つオブジェクトからRPCモジュールとexportを一意に特定する。構造欠落、読み込み失敗、候補の曖昧さはエラーとする。インストール先内部へのパス制約、同梱Electronの使用、OS/CPU照合は維持する。ホスト実装を複製したり、別の通信方式へ切り替えたりしない。

応答と通知の検証を維持する。ProviderError.diagnosticとログには型と出力項目を限定した診断情報を渡し、バージョン、OS/CPU、失敗段階、操作、エラーコード、検証箇所を保持する。ネイティブのエラーメッセージ・標準エラー出力・会話・認証情報は出力せず、利用者が内容を確認してIssueを作成する。自動投稿は行わない。providerのバージョンはpackage.jsonを唯一の管理元とし、ビルド時にserver内へ生成する。Paseoが禁止するrootモジュールの直接importには依存しない。

この決定はADR 2・3の完全一致による互換性制限、およびADR 4の対応バージョンの定義を修正する。Provider APIへの直接接続、OS別の配置解決、リリース通知の重複防止などの方針は引き続き適用する。

### Consequences

- Good, because バージョン番号・ハッシュ・短縮名の変更だけで利用を止めない。
- Good, because 障害の報告に必要な情報を、会話や認証情報を公開せずに共有できる。
- Bad, because 未検証の更新は起動後に失敗する場合があり、形式を保った意味の変更は検出できるとは限らない。
- Bad, because 非公開のクラス構造や配置が変わった場合は引き続き調査と実装修正が必要になる。

### Confirmation

最低バージョン境界、patch・minor・major、プレリリース、不正・不明な版、RPCファイル名・export名・ハッシュの変更、構造欠落、候補の曖昧さ、パス逸脱をテストする。起動・応答・通知・タイムアウト・プロセス終了で診断情報が保持され、秘密情報を出力しないことを確認する。リリース監視の基準を検証する。実ホストの初期化・モデル一覧取得と、Paseoの実コンパイラ・アダプターを用いた検証を行い、模擬した新バージョンの結果とは区別して記録する。

## More Information

[検証記録](../verification.md)と[利用者向けの報告手順](../../README.md#troubleshooting)を参照する。実際の破壊的変更への対応時には、通信実装と最低バージョンを合わせて見直す。公式SDKが必要な機能を公開した場合は、非公開RPC構造への依存を再検討する。
