# サーバー設定APIの追加後も診断専用画面を維持する

## Context and Problem Statement

ADR 8 は、Paseo がサーバー側の設定読取 API を公開した場合に判断を見直すと定めた。Paseo 0.9.0-beta.1 で `server.registerSettings()` が `read()` / `subscribe()` を持つハンドルを返すようになり、この再検討条件を満たした。ADR 8 の「daemon 側から保存値を読めない」という制約は 0.8.0 当時のもので、0.9.0-beta.1 には当てはまらない。

Issue #15 の対象はリリースへの互換性対応であり、インストール先を画面で編集する要求は含まれない。現在の診断と Provider は追加 API を採用せずに動作し、最低要件の Paseo 0.8.0 も引き続き対応対象である。

## Decision Drivers

- 公開 API の追加を評価し、解消した技術的制約を現在の制約として説明しない。
- 互換性対応に設定編集、二つの設定元の優先順位、セッションへの動的適用といった別の機能設計を持ち込まない。
- 必要な機能が増えていない段階で Paseo の最低要件を上げない。

## Considered Options

- 現在の要求範囲に基づいて診断専用画面を維持する。
- 公式 Settings API によるインストール先の編集機能を今回追加する。

## Decision Outcome

Chosen option: "現在の要求範囲に基づいて診断専用画面を維持する", because サーバー側の設定読取は可能になったが、今回の互換性対応には設定編集機能が必要ないためである。

ADR 8 の読み取り専用画面、専用 RPC、診断情報の秘匿方針を維持し、その判断理由と再検討条件を本 ADR で補足する。インストール先は引き続き daemon の `PASEO_ZCODE_INSTALL` で設定する。ZCode 側の認証・モデル設定を管理する API が追加されたわけではない。Provider 実装・会話の保存形式・manifest の最低要件 `>=0.8.0` は変更しない。

将来、画面からインストール先を編集する要求が生じた場合は公式 Settings API を前提に設計する。その際は環境変数との優先順位、既存セッションへの適用時点、無効な保存値の扱いを決め、採用 API を提供する Paseo バージョンへ最低要件を合わせる。標準 Provider 診断欄への接続 API が公開された場合も再評価する。

### Consequences

- Good, because 診断という現在の機能を保ち、0.8.0 を引き続き利用できる。
- Good, because API の制約と、機能を要求範囲外とする判断を区別できる。
- Bad, because サーバー側で設定を読める新しい Paseo でも、インストール先の変更は引き続き環境変数の手動設定になる。

### Confirmation

0.9.0-beta.1 の公開型定義と設定 API の説明で `read()` / `subscribe()` を確認する。型検査・全テスト・ビルドに加え、同版と最低要件 0.8.0 の実コンパイラ・Provider アダプターで登録と既存機能を検証する。実 daemon/UI の検証とは区別し、結果と未実施範囲は [検証記録](../verification.md) に残す。
