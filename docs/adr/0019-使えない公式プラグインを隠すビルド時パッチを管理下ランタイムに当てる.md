# 使えない公式プラグインを隠すビルド時パッチを管理下ランタイムに当てる

## Context and Problem Statement

プロバイダが起動する ZCode は、Desktop と `~/.zcode` を共有する。そのため、Desktop が `~/.zcode/cli/plugins` に展開した公式プラグインも読み込む。2026-10-09 の[検証](../verification.md)で、そのうち Computer Use と Browser Use はプロバイダからは動かないことを確かめた。

- Computer Use の Helper は、ZCode のコード署名を持たない起動元を拒否する。モデルが呼ぶと 60 秒でタイムアウトし、そのたびに Helper の起動が試みられる。
- Browser Use の実行先を Server に渡すのは Desktop のホストだけで、プロバイダの Server は常に空の一覧を返す。

それでもモデルには、`computer-use`、`control-browser`、`web-gui-tester` のスキルと、実行用の `mcp__node_repl__js` が見える。

公式の手段で止められるのは実行までである。Server に `ZCODE_CUA_PRODUCT_HELPER=0` を渡すと Computer Use がすぐ失敗し、ターン単位の `toolDisallowlist` で `mcp__node_repl__js` を隠せる。しかしスキル一覧からは消せない。

- ZCode のコメントには「`ZCODE_CUA_PRODUCT_HELPER` を切ると computer-use がどこからも見えなくなる」とある。しかし抑止用の集合は作られるだけで使われていない（`apps/zcode-cli/packages/bootstrap/src/app/bundled-plugins.ts` の `resolveOfficialPluginRoots`）。ZCode は Issue を受け付けておらず、上流での修正は期待できない。
- `app-server` には設定やプラグインを指定する引数が無い。環境変数で上書きできる設定も、ストレージ・ネットワーク・ログ・並列数に限られる。
- ユーザー設定で無効にすると Desktop も変わる。ワークスペースの設定で無効にすると、利用者のリポジトリにファイルを書き込む。

これまでは AGENTS.md と [ADR 15](0015-プラグイン管理のzcodeランタイムとnode-jsを設定画面から導入する.md) で、ZCode を改変せず、無改変の公式ソースだけを使うと決めていた。この制約のもとでは、スキルを隠す方法が無い。

## Decision Drivers

- プロバイダの ZCode でだけ、使えない機能をモデルから隠す。Desktop の表示や設定は変えない。
- サインイン、ユーザー設定、会話履歴、Desktop が導入した他のプラグインは、引き続き Desktop と共有する。
- 配布するランタイムを、再現でき、中身を確認でき、由来を証明できる状態に保つ。Apache-2.0 の改変物の条件を満たす。
- ZCode の更新ごとの作業を小さくし、パッチが当たらなくなったら確実に失敗させる。
- ZCode の利用者データや設定ファイルを、プラグインが直接書き換えない。

## Considered Options

- 無改変のランタイムを維持し、公式の手段（`ZCODE_CUA_PRODUCT_HELPER=0` と `toolDisallowlist`）だけで実行を止める。
- `ZCODE_STORAGE_DIR` で、プロバイダの ZCode の保存領域を Desktop と分ける。
- 分けた保存領域に、Desktop のプラグインキャッシュから使えるものだけを写す。
- 利用者の環境で、展開したランタイムのファイルを書き換える。
- エージェントの起動時に `--require` などで処理を差し替える。
- このリポジトリのリリース用ワークフローで、ソースに最小限のパッチを当ててからビルドする。

## Decision Outcome

ユーザーの選択に従い、「リリース用ワークフローで、ソースに最小限のパッチを当ててからビルドする」を採用する。スキルを隠せて、Desktop との共有を保ち、配布物の再現性と由来の証明も維持できるのはこの方法だけである。ADR 15 のうち「無改変の公式ソースだけを使う」を、この ADR の条件を満たすパッチに限って改める。その他の決定（取得元、ハッシュの固定、配置、設定画面からの導入、Desktop へのフォールバックをしないこと）は変えない。

**パッチの内容.** 最初のパッチは 1 つだけとする。すべてのプラグイン探索が通る `NodePluginAdapter.discoverPluginsSync`（`apps/zcode-cli/packages/adapters/src/plugins/index.ts`）に手を入れる。ここには、公式プラグインを `suppressedBuiltins` で外す既存の判定がある。その判定に、探索要求の `env` にある `PASEO_ZCODE_SUPPRESSED_PLUGINS`（カンマ区切りのプラグイン ID）に含まれる場合を加える。設定ファイルには書き戻さないので、Desktop には影響しない。上流の名前空間と衝突しないように、変数名は `PASEO_` で始める。`29628c9` に対する試作は、1 か所で 8 行追加・1 行削除だった。

**パッチの形式.** パッチは、ビルド前の TypeScript ソースに対する通常の差分（unified diff）とし、`git apply` で当てる。行番号ではなく前後の行の一致で位置を決めるため、上流が離れた場所を変えて位置がずれても当たる。周囲の行が変わると当たらずに失敗する。この失敗は、上流が該当箇所に手を入れたときに見直す合図として扱う。fuzz（文脈の一部不一致を許す当て方）は使わない。ビルド後の `zcode.cjs` は書き換えない。束ねる過程で変数名が変わるためである。AST を使った書き換えも採らない。避けられるのはコメントや整形の変更による失敗だけで、そのために書き換えのプログラムと依存を保守し、結果のコードを別に確かめる必要が出るからである。どの形式でも「当たったが効いていない」は検出できないので、効果は Confirmation の契約試験で確かめる。

**プロバイダの設定.** Server を起動するときに `PASEO_ZCODE_SUPPRESSED_PLUGINS=computer-use@zcode-plugins-official,browser-use@zcode-plugins-official` を渡す。両方を外すと、ZCode は `node_repl` も登録しない（どちらかが有効なときだけ登録する）。`ZCODE_CUA_PRODUCT_HELPER=0` とターン単位の `toolDisallowlist: ["mcp__node_repl__js"]` も併せて使い続ける。`PASEO_ZCODE_RUNTIME` で指定した無改変のランタイムでもこの 2 つは効き、パッチが外れた場合の備えにもなる。

**パッチの条件.** パッチは次の条件をすべて満たすものに限る。

- `patches/zcode/` に置き、Apache-2.0 で提供する。各ファイルの冒頭に、目的、対象のソースの場所、外せる条件を書く。
- 対象は、プロバイダが提供できない機能をモデルや一覧から外すことに限る。モデル要求、認証と認証情報、保存形式、プロトコル、通信先は変えない。
- リリース用ワークフローで、ビルドの前に `git apply --check` してから適用する。当たらなければビルドを失敗させる。
- 上流に同等の公式の手段ができたら、パッチを外してそれに切り替える。

**配布物の表示.** `BUILD-INFO.json` は `modified: true` とし、適用したパッチのファイル名と SHA-256 を記録する。パッチのファイル自体を配布物に同梱する。リリースノート、README、NOTICE.md では「公開ソースに `patches/zcode/` のパッチを当てた非公式ビルド」と書く。これで Apache-2.0 第 4 条 (b) の「変更したことの明示」を満たす。

**版の付け方.** タグは `zcode-runtime-v<ZCode の版>-paseo.<n>`、成果物は `zcode-runtime-<ZCode の版>-paseo.<n>.tar.gz` とする。`<n>` は同じ ZCode の版に対するパッチの改版番号である。既存の `zcode-runtime-v3.14.3` は無改変のまま残し、差し替えない。`server/runtime/pins.ts` は新しい成果物を固定する。固定が変わると、利用者は設定画面から導入し直す（これまでの更新と同じ）。

### Consequences

- Good, because プロバイダの ZCode では、使えないスキルと `node_repl` がモデルから見えなくなる。Desktop の表示と設定は変わらない。
- Good, because サインイン、ユーザー設定、会話履歴、Desktop が導入した他のプラグインの共有を保てる。
- Good, because パッチはリポジトリ上で読め、配布物は CI の署名で由来を証明できる。
- Bad, because 配布物は無改変ではなくなる。利用者はパッチの中身も信頼する必要がある。
- Bad, because ZCode を更新するたびに、パッチの適用と効果の確認が要る。上流が探索の処理を変えると、パッチの書き直しが要る。
- Bad, because このリポジトリが、改変した Apache-2.0 の成果物の再配布者になる。
- Bad, because `PASEO_ZCODE_RUNTIME` で無改変のランタイムを使う場合はスキルが見えたままになる。実行は公式の手段で止まる。
- Neutral, because 利用者が Desktop で有効にしたプラグインを、プロバイダでは意図して外す。プロバイダの ZCode では `enabledPlugins` の値と見え方が一致しない。

### Confirmation

リリース用ワークフローと CI の契約試験で、隔離した保存領域に computer-use と browser-use の公式プラグインの模擬キャッシュを置いて確かめる。

- 変数があるとき：`listPlugins` とスキル一覧から両方が消え、`node_repl` が登録されない。
- 変数が無いとき：両方とも現れる。

あわせて、5 プラットフォームで `test:stdio-runtime` が通ることを確かめる。実環境では、Desktop が導入したキャッシュがある状態で、モデルに渡るスキル一覧とツール一覧に該当するものが無いことをモデル入出力ログで確認し、[検証記録](../verification.md)に残す。

## Pros and Cons of the Options

### 無改変のランタイムを維持し、公式の手段だけで実行を止める

- Good, because 配布物の「無改変」を保て、ZCode を更新するときのパッチ作業が無い。
- Good, because Computer Use と Browser Use はすぐ失敗し、Helper も起動しない（検証で確認済み）。
- Bad, because スキルは一覧に残る。モデルはスキルを読み込んでから、使えないことに気付く。

### `ZCODE_STORAGE_DIR` で保存領域を分ける

- Good, because ZCode を改変せずにスキルを隠せる。サインイン、ユーザー設定、会話 DB、HOME 基準のユーザースキルは共有したままになる（検証で確認済み）。
- Bad, because Desktop 同梱の公式プラグインがすべて消える。文書系スキル、image-search、zcode-guide、skill-creator、plugin-creator が該当する。これらはソースが公開されておらず CDN のマーケットプレイスにも無いため、公式の手段で入れ直せない。
- Bad, because `~/.zcode/agents` のサブエージェント定義、メモリ、添付やツール出力の保存先も Desktop と分かれる。

### 分けた保存領域に、使えるプラグインだけを写す

- Good, because ZCode を改変せずに、使えるプラグインを残せる。
- Bad, because ZCode のプラグインキャッシュをプラグインが直接読み書きすることになる。キャッシュの形式や seed の検査に依存し、ZCode の更新で壊れやすい。

### 利用者の環境で、展開したファイルを書き換える

- Good, because 配布物そのものは無改変のまま残る。
- Bad, because SHA-256 で検証した配布物と、実際に動く中身が食い違う。診断のハッシュ表示も意味を失う。

### 起動時に処理を差し替える

- Good, because 配布物にも、展開したファイルにも手を入れない。
- Bad, because ファイルは無改変のまま挙動だけが変わり、外から見て分からない。まとめてビルドされた `zcode.cjs` の内部に依存するため、最も壊れやすい。

### リリース用ワークフローで、ソースにパッチを当ててからビルドする

- Good, because 公式の `build-zcode.mjs` でビルドでき、パッチは差分として確認でき、ビルドと署名の流れも変わらない。
- Good, because ZCode に既にある `suppressedBuiltins` の仕組みを使うので、差分が小さい。
- Bad, because 上の Consequences の Bad をすべて負う。

## More Information

ADR 15 を部分的に改める。AGENTS.md、`docs/development.md`、`docs/todo.md` の「ZCode を改変しない」という記述は、この ADR の条件を満たすパッチを例外とする形に改める。上流で、`ZCODE_CUA_PRODUCT_HELPER` の抑止が働くようになった場合や、プラグインを外す公式の手段ができた場合は、パッチを外して再評価する。Browser Use の実行先が単体の Server でも使えるようになった場合は、外す対象から browser-use を除く。
