# /goalをV4のゴール用コマンドで送り、ゴールの状態を入力欄上のピルで表示する

## Context and Problem Statement

ZCode Desktop は、会話の右上の状態パネルに Goal を表示する。内容は、経過時間と、反復ごとの行（題と、その反復のタスクの完了数）である。利用者から、Paseo でも同等の表示が欲しいと求められた。

調べると、表示より前に、Paseo からはゴールを設定できていなかった。

- プラグインは ZCode の `slashCommands` をそのまま Paseo のコマンド一覧に出しており、`goal` も含まれる。一方、入力はすべて V4 の `sendText` で送っていた。Server のテキスト入力は `/goal` を解釈しない。Desktop は `/goal` を自分で読み、`sendGoalCommand`・`resumeGoal`・`pauseGoal` を送る（a9fe401 の `packages/ui/src/v4/slashCommands.ts` と `SessionPane.tsx` の `dispatchSlashCommand`。Server 側は `apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/commands/handlers/goal-compact.ts`）。管理下ランタイム 3.17.2 で確かめると、`sendText` で送った `/goal <目標>` はそのままモデルへのユーザーメッセージになり、V4 の `goal` は `null` のままだった。
- Paseo のプロバイダー API とプロトコルには、ゴールに当たる概念が無い。常に見える場所に出せるのは、0.15.0 からあるクライアントの `addComposerPill` である。エージェントごとに、入力欄の上の Tasks や Subagents と同じ行へピルを足す。
- ピルを出すクライアントは、ゴールの状態を持つプラグインのサーバーから値を読む必要がある。ここに制約が二つある。Paseo がプロバイダーに渡すセッション ID は、開くたびに変わる Paseo 独自の UUID で、エージェント ID ではない（v0.15.0 の `plugin-provider.ts`）。また 0.15.4 までの Paseo には、プラグインのサーバーからクライアントへ知らせる仕組みが無い。プラグインの subscription とエージェントのメタデータは、0.16.0 のベータ（0.16.0-beta.1 以降）にだけある。

## Decision Drivers

- Paseo のコマンド一覧に出ている `/goal` が、Desktop と同じ結果になる。
- 表示の内容は Desktop の Goal 欄に合わせ、独自の解釈を足さない。
- Paseo と ZCode の公開された手段だけを使い、最低要件の 0.15.0 を上げない。
- ゴールの変化を取りこぼさない。ゴールを使っていない間は通信を増やさない。
- ADR 9 の実行の対応付けと、受付を ACK の後に知らせる規則を崩さない。

## Considered Options

- `/goal` を V4 のゴール用コマンドで送り、状態を RPC から読んでピルに出す。読む契機は、ZCode のエージェントの更新と、進行中の一定間隔とする。
- 状態をタイムラインの行としてだけ出す。
- ゴールを todo（Paseo の Tasks）に混ぜる。
- Paseo の subscription が正式版（0.16.0）に入るのを待ち、最低要件を上げて通知で実装する。
- RPC の応答を保留し、変化があったときに返す（ロングポーリング）。

## Decision Outcome

Chosen option: "`/goal` を V4 のゴール用コマンドで送り、状態を RPC から読んでピルに出す", because 今の最低要件のまま、公開された手段だけで、Desktop と同じ内容を常に見える場所に出せる唯一の選択肢だからである。

### コマンド

- `/goal` と別名の `/target` は、コマンドとして届いた場合も、単独のテキストとして届いた場合も、プラグインが Desktop と同じ規則で読む（`server/goal-command.ts`）。動作は先頭の語で決まる。
  - `<目標>` と `replace <目標>` は `sendGoalCommand` で送る。`text` は目標、`displayText` は入力そのまま、あとは現在のモデルの選択と `mode`、`planEnabled: false` である。既にゴールがあれば、Server が置き換える。
  - `resume` は `resumeGoal` で送る。
  - `pause` は `pauseGoal` で送る。Desktop ではボタンの操作で、テキストの `/goal pause` には対応していない。Paseo にはボタンが無いので、ZCode の端末の UI と同じくコマンドに割り当てる。ターンは始まらないので、`session.prompt_result` は `completed` で返す。既に `paused` のときは、何も送らずに同じ結果を返す。実行中に打たれたコマンドは、Paseo がそのターンを止めた後に届き、その時点でゴールは一時停止しているためである。
  - 引数が無い場合と `clear`・`show` は、何も送らず、理由を書いた `INVALID_CONFIGURATION` で失敗にする。V4 に対応するコマンドが無い。
  - 添付が付いた `/goal` と、複数のテキストに分かれた `/goal` も失敗にする。テキストとして送ると、モデルがそのまま読むためである。
- Plan が有効な間は、ゴールを設定も再開もしない。Server が両立を拒否する（`guard.planGoalMutuallyExclusive`）ので、送る前に固定の文言で失敗にする。`resume` と `pause` は、V4 の `availability.resumeGoal` と `availability.pauseGoal` が許すときだけ送る。
- ほかのコマンドと同じく、実行中のターンが無いときだけ受け付ける。進行中のゴールは、Paseo の停止で一時停止できる。Server は、ターンを止めるとそのゴールを `paused` にする。実行中に打たれたコマンドをプラグインが断ると、Paseo はそのターンを止めてから送り直す（Paseo の公開ドキュメントにある、ステアリングできない場合の扱い）。
- `sendGoalCommand` と `resumeGoal` は、Paseo の実行を一つ始める（ADR 9 の拡張）。Server は、コマンド自体のターン（`executionKind: "controlOnly"`、`userInput` 行つき）と、ゴールに向けて自分で始めるターン（`origin: "goalContinuation"`）を作る。両方をその実行に含め、検証（`goalVerifier`）が終わって会話がアイドルになったときに完了にする。検証が未達で、アイドルにならずに次の反復が始まる場合は、同じ実行が続く。
- `sendGoalCommand` の ACK は `inputAccepted` の結果を持たず、ターンの行より後に届く。受付の通知は、これまでどおり ACK を待つ。`resumeGoal` は `userInput` 行を作らないので、始まったターンのヘッダーを実行の根拠にする。
- `sendGoalCommand` は `toolDisallowlist` を受け取らない。ゴールのターンには、ADR 19 のターン単位の指定が付かない。管理下ランタイムでは、パッチと `PASEO_ZCODE_SUPPRESSED_PLUGINS` が従来どおり隠す。

### 状態の読み出し

- プロバイダーは、`session.open` の `config.env.PASEO_AGENT_ID` を鍵にして、開いているセッションを登録する（`server/goal.ts` の `GoalDirectory`）。Paseo は、プロバイダーのセッションを開く前に、必ずこの変数を起動環境に入れる（v0.15.0 の `public-docs/plugins/hooks.md` の順序と、`agent-manager.ts` の `buildLaunchContext`）。
- RPC `zcode.goals` は、ゴールを持つセッションごとに、エージェント ID、状態、経過秒、時間が進んでいるか、反復ごとの行（番号、題、完了数、総数、完了したか）を返す。入力は無い。
- 行と経過時間は、Desktop の `packages/ui/src/v4/conversationGoalSummaryModel.ts` を固定ソースから `server/vendor/zcode` に取り込み、そのまま使う。`check:zcode-source` の対象にするので、基準を更新したときに上流の変更が分かる。
- 経過秒は daemon の時計で計算して返す。クライアントは、受け取ってからの時間を自分の時計で足す。端末と daemon の時計のずれを避けるためである。
- RPC は目標の題を返す。同じホストのクライアントは、タイムラインで同じ内容を読めるので、見える範囲は変わらない。

### ピル

- クライアントの入口で `client.paseo.agents.list({ subscribe: {} })` を購読し、`provider` が `zcode` のエージェントとそのワークスペースを把握する（`client/goal-pills.ts`）。Paseo の公式のサンプル（`plugin-examples/local-plugin`）と同じ形である。
- `zcode.goals` を読む契機は三つある。一覧のスナップショット、ZCode のエージェントの更新、進行中のゴール（`active`・`verifying`・`notSatisfied`）のピルがある間の 10 秒ごとである。読む間隔は 1 秒以上あける。
- 10 秒ごとに読むのは、Paseo から見える変化を伴わないゴールの変化があるためである。3.17.2 では、題（`summaryTitle`）がターンの開始より後に付く。
- ゴールがあるエージェントに、`addComposerPill`（ID は `goal`）でピルを出す。ラベルは `Goal 1h 3m`（分単位の経過時間）、アイコンは状態ごと、タイトルは `Goal: <状態>` である。更新は `update()` でラベル・アイコン・タイトルだけを変える。`behavior` を渡すと、開いているポップオーバーが閉じるためである。ゴールが無くなれば消す。
- ピルを押すと、ポップオーバー（狭い画面ではシート）が開き、状態、秒単位の経過時間、反復ごとの行を出す（`client/goal.tsx`）。開いている間は、進行中なら 3 秒ごとに読む。操作のボタンは置かず、`/goal resume` と停止についての案内を一行出す。

### Consequences

- Good, because `/goal` が Paseo から使えるようになる。これまではモデルにテキストとして渡り、ゴールは設定されなかった。
- Good, because Desktop の Goal 欄と同じ行・件数・経過時間が、入力欄の上に常に出る。
- Good, because 最低要件を変えず、Paseo と ZCode の公開された手段だけで実現できる。
- Bad, because 通知の仕組みが無いので、進行中は 10 秒ごとの読み出しが要る。題の変化などは、最大で 10 秒遅れて反映される。
- Bad, because セッションが開いていないエージェントには、開き直すまでピルが出ない。アイドル時に解放された後と、daemon を再起動した後がこれに当たる。ゴールは ZCode の Server が動いていないと読めない。
- Bad, because `/goal clear` が無い。ゴールを無くす手段は、新しいゴールでの置き換えだけである。
- Bad, because 先頭の語が `pause`・`resume`・`clear`・`show`・`replace` の目標は、そのままでは設定できない。ZCode 自身と同じ制約である。
- Bad, because `PASEO_ZCODE_RUNTIME` の未パッチのランタイムでは、ゴールのターンにターン単位のツールの非表示が付かない。Desktop で Browser Use か Computer Use を有効にしていると、そのターンのモデルに `mcp__node_repl__js` が見える。バックグラウンドの結果を届けるターンと同じ扱いで、`ZCODE_CUA_PRODUCT_HELPER=0` は従来どおり効く。
- Bad, because エージェントの一覧は 1 回の取得で 200 件までなので、それを超えるホストでは、一覧に入らなかったエージェントのピルは、そのエージェントに更新があるまで出ない。
- Neutral, because Paseo 0.16.0 の正式版が出れば、読み出しの契機を subscription の通知に置き換えられる。そのときに最低要件とあわせて見直す。

### Confirmation

- `server/goal-command.test.ts` で読み方を、`server/goal.test.ts` で表示用の値と登録簿を確認する。
- `test/goal.test.ts` で、`/goal` が `sendText` ではなく `sendGoalCommand` で送られること、未達で継続した実行が達成まで一つのターンであること、受付の通知が ACK の後であること、停止による一時停止と `resume`、ターンの無い `pause`、送らない場合の失敗の文言、Server に拒否されてもセッションが使えること、登録簿が `PASEO_AGENT_ID` のあるセッションだけを閉じるまで載せることを確認する。
- `test/goal-pills.test.ts` で、ピルの登録・更新・削除、読む契機と間隔、クライアントの時計での経過時間、読み出しの失敗からの回復を確認する。
- `npm run test:upstream`（v0.15.3）で、Paseo の実コンパイラでビルドしたクライアントの入口がピルを登録して片付けること、実アダプター経由の `/goal Ship it` が `sendGoalCommand` になること、起動環境の `PASEO_AGENT_ID` でゴールを引けることを確認する。
- `npm run test:stdio-runtime` で、実ランタイムと固定の応答を返すモデルを使い、設定から未達での継続を経て達成までが一つのターンで終わること、停止でゴールが `paused` になること、`/goal resume` で再開して達成することを確認する。

## Pros and Cons of the Options

### `/goal` を V4 のゴール用コマンドで送り、状態を RPC から読んでピルに出す

- Good, because Desktop と同じコマンドと同じ表示の規則を使う。
- Good, because Paseo 0.15.0 の `addComposerPill`・`rpc`・エージェントの一覧の購読だけで足りる。
- Bad, because 進行中は一定間隔の読み出しが残る。

### 状態をタイムラインの行としてだけ出す

- Good, because クライアントの変更が要らない。
- Bad, because 会話が進むと流れていき、今の状態と経過時間が常には見えない。
- Bad, because Paseo は届いた通知を追記するので、状態が変わるたびに行が増える。

### ゴールを todo（Paseo の Tasks）に混ぜる

- Good, because 既存の Tasks のピルに出る。
- Bad, because ゴールはタスクではなく、Tasks の完了数の意味が変わる。経過時間と反復の区切りも表せない。

### Paseo の subscription が正式版（0.16.0）に入るのを待ち、最低要件を上げて通知で実装する

- Good, because 一定間隔の読み出しが要らなくなる。
- Bad, because 正式版が出るまで表示が無い。出た後は、最低要件を 0.16.0 に上げることになる。

### RPC の応答を保留し、変化があったときに返す

- Good, because 変化をすぐに反映できる。
- Bad, because Paseo は RPC を 30 秒で打ち切る（v0.15.0 の `plugins/runtime.ts` の `REQUEST_TIMEOUT_MS`）。これは文書に無い内部の値で、それに合わせた保留時間に依存することになる。

## More Information

- 見直す条件は三つある。Paseo 0.16.0 の正式版が出て、subscription とエージェントのメタデータが使えるようになったとき。ZCode が V4 にゴールを消すコマンドを加えたとき。`sendGoalCommand` が `toolDisallowlist` を受け取るようになったとき。
- 検証の記録は [verification.md](../verification.md) にある。
