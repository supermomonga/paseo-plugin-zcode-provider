# 入力が読まれた根拠にターンのヘッダーを加え、実行を名乗らない作業は対象を指定せずに停止する

## Context and Problem Statement

Paseo から `/compact` を送ると、圧縮は実行されるが、Paseo のターンが完了しなかった。停止を押すまで、エージェントは実行中のままになる。圧縮の最中に停止を押すと、今度は停止が失敗してセッションが閉じた。管理下ランタイム 3.17.2 で確かめると、原因は二つあった。

- **完了**：プラグインは、受け付けた入力がすべて ZCode に読まれるまで実行を完了にしない（ADR 9）。読まれた根拠は、その入力のコマンド ID（`sourceCommandId`）を持つ `userInput` 行だけだった。Server は `/compact` をテキストから読んで圧縮する（a9fe401 の `apps/zcode-cli/packages/core/src/runtime/helpers/commands.ts` の `parseCompactCommand`）。このターンには `userInput` 行が無く、コマンド ID を持つのはターンのヘッダーと `compact` のマーカーである。そのため入力は読まれていない扱いのまま残った。
- **停止**：プラグインは、停止できる状態（`control.canStop`）なのに、`activeWorks` のどれも `foregroundExecutionId` を持たないと、プロトコルの誤りとして扱っていた。手動の圧縮の間、`activeWorks` は `primaryTurn` と `compact` の二つで、どちらも `foregroundExecutionId` を持たない（`stopTargetKind` は `mixed`）。Desktop は、この場合に対象を指定しない `stop` を送る（a9fe401 の `packages/ui/src/v4/SessionPane.tsx` の `handleStop`）。

テキストで解釈されるほかのコマンド（`/rewind`、`/fork`）と、プロンプトに展開されるコマンド（`/init`、`/workflow`）には `userInput` 行があり、完了していた。

## Decision Drivers

- ZCode が案内している `/compact [instructions]` を、指示つきのまま使える。
- 完了と停止の判断には、V4 が投影する状態だけを使う。
- `/compact` だけの特別扱いを増やさない。
- ADR 9 の、受け付けたすべての入力が読まれてから完了にする規則を保つ。

## Considered Options

- 読まれた根拠にターンのヘッダーを加え、実行を名乗る作業が無いときは対象を指定せずに停止する。
- `/compact` を、Desktop と同じく V4 の `compact` コマンドで送る。
- `compact` のマーカーを、`/compact` の入力が読まれた根拠として特別に扱う。

## Decision Outcome

Chosen option: "読まれた根拠にターンのヘッダーを加え、実行を名乗る作業が無いときは対象を指定せずに停止する", because 指示つきの `/compact` を保ったまま、コマンドごとの特別扱いを足さずに、二つの原因をどちらも直せるからである。

- 受け付けた入力は、そのコマンド ID を持つ `userInput` 行か `turnHeader` 行が現れたときに、読まれたとみなす（`server/session.ts` の `observe`）。ヘッダーの `sourceCommandId` は、そのターンを始めたコマンドを指す。
- 同じコマンド ID を持つヘッダーが後から現れても、もう一度読まれたとは扱わない。ゴールに向けた各ターンのヘッダーは、ゴールを設定したコマンドの ID を持ち続ける（ADR 27）。
- `/compact` は、これまでどおり `sendText` で送る。V4 の `compact` コマンドは指示を受け取らない。`/compact keep the API notes` をテキストで送ると、要約のリクエストに `Additional Instructions:` として指示が入ることを確かめた。
- 停止は、`foregroundExecutionId` を持つ作業があればその ID を指定し、無くて `control.canStop` が真なら、対象を指定せずに送る（`server/session.ts` の `stop`）。ID を持つ作業があるときに指定する扱いは変えない。

### Consequences

- Good, because `/compact` のターンが、成功・圧縮するものが無い場合・失敗のどれでも完了する。失敗は ADR 23 の分類で伝わる。
- Good, because 圧縮の最中に停止でき、セッションが閉じない。
- Good, because `userInput` 行を作らないターンが今後増えても、同じ規則で完了する。
- Bad, because 対象を指定しない停止は、遅れて届くと、その間に始まった別の実行を止めうる。ID の指定はこれを防ぐためのものである。プラグインは状態を見てすぐに送るので、Desktop と同じ範囲の危険にとどまる。
- Neutral, because `/compress` は扱わない。Desktop だけの別名で、Server のコマンド一覧にもテキストの解釈にも無い。

### Confirmation

- `test/compact.test.ts` で、`userInput` 行の無い圧縮のターンが完了すること、失敗が失敗したターンとして伝わること、実行を名乗らない作業を対象の指定なしで停止できることを確認する。ヘッダーを根拠から外すと前の二つが、停止の変更を外すと最後の一つが失敗する。
- `npm run test:stdio-runtime` で、実ランタイムと固定の応答を返すモデルを使い、指示つきの `/compact` が完了して指示が要約のリクエストに入ること、圧縮の最中の停止でターンが取り消されて次の入力が通ることを確認する。
- `npm run test:upstream` で、Paseo の実アダプターを通した `/compact` の完了と停止を確認する。

## Pros and Cons of the Options

### 読まれた根拠にターンのヘッダーを加え、実行を名乗る作業が無いときは対象を指定せずに停止する

- Good, because Server の公開している状態だけで決まり、コマンドの種類に依存しない。
- Good, because 指示つきの `/compact` が使える。
- Bad, because 対象を指定しない停止が加わる。

### `/compact` を、Desktop と同じく V4 の `compact` コマンドで送る

- Good, because Desktop と同じコマンドになり、二重の圧縮を Server が断る。
- Bad, because V4 の `compact` は指示を受け取らないので、ZCode が案内している `/compact [instructions]` の指示が捨てられる。
- Bad, because このコマンドでも `userInput` 行は作られないので、完了の根拠の問題は残る。

### `compact` のマーカーを、`/compact` の入力が読まれた根拠として特別に扱う

- Good, because 変更が圧縮だけに閉じる。
- Bad, because 行の種類ごとの特別扱いが増え、同じ形のターンが増えるたびに足すことになる。
